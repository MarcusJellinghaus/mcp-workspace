Document GitHub write tools and switch issue skills to them

Add the five write tools to CLAUDE.md's tool-mapping table and take the
commands they replace off the Bash allowlist: gh issue create, gh issue
edit and gh pr create are gone, and gh issue comment now carries the same
cross-repo carve-out gh issue view already had. The MCP tools are
repo-auto-detected, so the --repo owner/repo path has no MCP equivalent.

The table and the allowlist are one statement read from two directions,
and the three issue skills declare and instruct the commands the
allowlist just dropped, so they change in the same commit:

- issue_create: "Bash(gh issue create *)" becomes
  github_issue_create; the body is passed inline.
- issue_update: "Bash(gh issue edit *)" becomes github_issue_edit, and
  the save_file -> --body-file -> delete_this_file tempfile dance
  collapses into one call. delete_this_file comes off allowed-tools with
  it; .scratch/issue_body_temp.md is no longer referenced anywhere.
- issue_approve: github_issue_comment is added for the current repo. The
  gh form stays for the documented cross-repo path, keeping the
  MSYS_NO_PATHCONV=1 note, which is a Git Bash workaround irrelevant to
  the MCP call.

The "Status labels" paragraph keeps its "never use raw gh issue edit with
label flags" wording; the guard it describes is still the rule, and the
new tools reject status-* labels themselves.

tests/LLM_Test.md gains Section 4, kept separate from Section 3 and
marked opt-in because it mutates real GitHub objects. It walks an issue
through create, comment, edit and close, covers the no-op label removal,
status-label and unknown-label guards, and scripts only the rejection
paths for github_pr_create.

.claude/settings.local.json is deliberately untouched: the write tools
stay off the global allowlist. A skill's allowed-tools grants a tool only
inside that skill, which is the same narrow grant the removed
"Bash(gh issue create *)" entries were.
