Add github_issue_edit MCP tool

Expose combined issue editing as an MCP tool, reusing the step-2
`IssueManager.edit_issue` and the step-3 `_check_labels` /
`_resolve_assignees` helpers unchanged. The status-label guard is passed both
the add and the remove side: removing a status label leaves zero, which makes
`_collect_github_label` fall back to DEFAULT_LABEL.

`edit_issue` has no transaction, so a failure at the label step leaves an
earlier scalar edit in place. Failure reaches the tool through two channels,
not one:

- the empty-IssueData sentinel, for a swallowed 404/422/5xx;
- a raised exception, because `_handle_github_errors` re-raises 401/403 and
  every ValueError — including the IssueIdentityMismatchError thrown by
  `edit_issue`'s own closing refetch, by which point every write has landed.

Both converge on one refetch-and-warn path, so no partial write is ever
reported as a bare `Error:`. The tool pre-validates `number` and `state`
itself so the exception channel cannot contain a pre-write failure and stays
readable as "the write sequence started and something after it failed"; the
library keeps its own identical checks for its other callers.

On that path the refetched state is compared against the request to render
`Applied:` / `Not applied:` lines naming only the arguments the caller
actually passed — no extra API call beyond the single `get_issue`, which is
paid only when something went wrong. Assignees are reported because a
non-assignable login succeeds silently with no effect.

Adds tests/github_operations/test_github_write_tools_issue_edit.py (17 tests)
in its own module — the create/comment module would pass the 750-line limit —
plus a vulture_whitelist entry for the tool.
